# ADR-0007: Doing onboarding once

- **Status:** ACCEPTED for the local half — MMKV chosen, written, pending a native build.
  The cross-install half is deferred.
- **Raised by:** Kyel, 8 October 2026

## The symptom

Onboarding runs on every launch.

## The cause, which is not onboarding

There is no persistence in the app at all. `grep` for AsyncStorage, MMKV,
SecureStore or Keychain returns nothing. `Root` hardcodes
`initialRoute = 'Welcome'` and holds the profile and goal in `useState`, so
every launch is a cold boot from the fixture.

Onboarding is not repeating. The app has no memory, and onboarding is simply
the first thing it does.

## Two problems wearing one coat

**1. Reopening the app.** The real irritation, and entirely solvable on-device.

**2. Reinstalling the app.** A different problem with a different answer, and
the one that cannot be solved properly without an account.

## 1. Reopening — persist locally, gate on a flag

Save the profile, the goal and a `hasOnboarded` flag; read them before the
first render; send a returning user to Today.

| | |
| --- | --- |
| **AsyncStorage** | The default. Asynchronous, so the first frame has to handle "not loaded yet" — a splash already covers that. |
| **MMKV** | Faster and synchronous, so the route is known before anything draws. A heavier native dependency. |

Either is a third-party install. The choice is Kyel's; the flag matters more
than the store.

**What persisting the profile does NOT mean.** A returning user should still be
asked to weigh in. The weight is a reading, not a setting, and ADR-0001's
targets follow from it.

## 2. Reinstalling — what each platform actually offers

Checked October 2026, because this behaviour has changed before.

| Platform | Mechanism | Standing |
| --- | --- | --- |
| iOS | Keychain | Survives deletion today, but **undocumented**. Apple tried to auto-delete keychain items in the iOS 10.3 beta and reverted after developer pushback. Expo has an open issue noting their own docs contradict the behaviour. |
| Android | Block Store | **Supported and documented** for exactly this. Needs Play Services and the user's backup turned on. |

So iOS offers an undocumented accident and Android offers a real API. There is
no symmetric answer, and on both a user who clears data or turns backup off
defeats it. Building the onboarding gate on the iOS keychain means resting it
on behaviour Apple has never promised and has already tried to remove once.

## Three reasons "never again, ever" is the wrong target

1. **A stale profile is worse than a question.** Someone reinstalling after a
   year has a different weight and probably a different goal. Re-asking is
   correct, not a failure.
2. **Phones change hands.** Device-level persistence hands a stranger's targets
   to the next owner of a hand-me-down phone.
3. **It contradicts a promise already on screen.** About you says data never
   leaves the phone. Anything that survives a wipe lives off-device — Block
   Store, iCloud or our own server — and that sentence then has to say what
   goes and what does not. A trust cost, not a footnote.

## Recommendation

Build the local half now: it fixes the actual complaint and commits to nothing.

Leave the cross-install half until invites and accounts, which the >20-user gate
needs anyway. Identity then carries the profile across reinstalls as a side
effect of something already being built — no keychain trick, no broken promise,
and it works on both platforms the same way.

## What was built, 8 October 2026

The gate, and nothing underneath it.

`SetupStore` in `src/store/setup.ts` is the seam: `read`, `write`, `clear`. `Root` reads it
before it chooses a first screen — showing the loading screen it already had while it waits —
and opens Today when there is a saved setup, or setup when there is not. Finishing setup writes.

**There is no `hasOnboarded` flag.** A flag and the answers can disagree, and a flag set with no
profile behind it opens Today on nothing. What is saved *is* the answers, so "has been through
setup" and "has a profile" cannot come apart.

A store that cannot be read counts as a store with nothing in it. Asking the four questions
again beats opening Today on a guess, so a rejected `read` and a record that does not type-check
as a setup both land on setup. `isSetup` is that check.

`memoryStore` is the implementation, and it is the dynamic mock: it honours the whole contract
and holds for the life of the process. So the gate is finished work and the complaint is *not
yet fixed* — a relaunch still asks the questions, because nothing is written to disk.

### MMKV against the nitro pin — checked 8 October 2026

Kyel picked MMKV on the reasoning that it rides the Nitro foundation vision-camera already
brought in. The versions do not line up, and the question is whether that matters.

| Package | Generated by nitrogen |
| --- | --- |
| `react-native-vision-camera@5.2.3` | 0.37.0 — why `react-native-nitro-modules` is pinned to exactly 0.37.0 |
| `react-native-mmkv@4.3.2` (latest) | 0.35.9 |

Both declare `"react-native-nitro-modules": "*"` as a peer, so neither constrains the other and
installing MMKV cannot move the pin. What it does mean is that MMKV's pre-generated C++, built
against 0.35.9 headers, compiles against the 0.37.0 pod — only one copy of that pod can exist
in a native build, and it is vision-camera's.

**Checked, rather than assumed.** All fifteen `NitroModules/*.hpp` headers MMKV's generated
code includes are present in 0.37.0. Thirteen are byte-identical between the two versions.
`NitroDefines.hpp` differs only in the `NITRO_VERSION` string. `JHybridObject.hpp` has a real
breaking change — `getOrCreateHybridObject()` gained a required argument, and `getJavaPart()`
and `_cxxJavaPart` were removed — but it is a JNI header, so Android only, and MMKV's generated
code calls none of the three: its `JHybridMMKVPlatformContextSpec` declares its own
`getJavaPart()`, not an override of the base one.

So there is no evidence of an incompatibility. This is a header analysis and not a build, which
is the only real proof — and the cost of finding out is one `pod install` and one compile, with
`yarn remove` as the way back.

Worth recording why this was checked at all: the earlier `'NitroModules/ReactProp.hpp' file not
found` failure in this project came from a nitro version mismatch, which makes "two nitro
versions" look like the same bug. It is not the same bug, and the resemblance is not evidence.

### Decided: MMKV — 8 October 2026

`react-native-mmkv` at **4.3.2, pinned exactly** — not a caret. It ships C++ generated against
a particular nitrogen, so a silent minor bump is a native build change, and that is the same
reason `react-native-nitro-modules` is pinned.

`mmkvStore` in `src/store/mmkv.ts` implements `SetupStore` over one key holding the whole setup
as JSON. One key and not a field each: a setup written field by field can be read back
half-applied if the process dies between two writes, and a key is either there and complete or
it is not there.

**`SetupStore` gained an optional `peek()`**, which is what MMKV was chosen for. `Root` calls it
in its state initialiser, so with a synchronous store the first screen is known in the first
render and the loading frame never draws. `peek` returns `undefined` for *cannot answer*, which
is not the same fact as `null` for *nothing saved* — answering `null` from a build with no pod
would send a returning user back through setup over a build problem. On `undefined`, `Root`
falls back to the asynchronous `read`, so AsyncStorage would still work behind this seam
unchanged.

**A missing pod does not stop the app.** The JS half of a nitro module looks healthy without
one, and `createMMKV` throws when called rather than when imported. It is called once, inside a
`try`, when the store is built: a build with no pod loses its memory of setup and nothing else.

`memoryStore` stays, as the store the navigator falls back to when it is handed none — that is
what keeps a screen walked on its own from writing to disk.

Until then there is no end-to-end flow for "the second launch skips setup", because there is
nothing for it to assert. `.maestro/onboarding.yaml` still walks the first launch and still
passes unchanged — the copy did not move.

## Not decided here

Which store. Whether a returning user is asked to weigh in (recommended: yes).
What Settings offers for starting again — there is no board for it, and a
destructive action with no way back is its own design problem.
